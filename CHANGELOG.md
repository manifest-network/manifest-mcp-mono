## [Unreleased]

### Added

- **core:** `@manifest-network/manifest-mcp-core/__test-utils__/fetch-probe.js`, a new subpath carrying the wire probe fred's `http/fred.test.ts` had held since ENG-705 — `fetchProbe` (answers one script for any URL) plus a new `sealedFetchProbe` (routes by last path segment, DENIES anything unrouted). It sits at `doFetch`, below every layer of the transport, so nothing the transport does internally can escape it; that is what removes the reason to `vi.mock` an HTTP module at all, and the real `validateProviderUrl` / `checkedFetch` / `readBodyCapped` / `classifyTransportError` / JSON parse then run on every assertion. A refusal is thrown at the caller **and** recorded in a ledger drained by an `afterEach`, because the throw alone is not enough: fred's transport re-wraps any `doFetch` rejection as `ProviderApiError{ kind: 'network' }`, so a test asserting a transport fault would otherwise go green on a request the probe refused — the same false-green `tools/vitest/ban-global-fetch.ts` exists to kill. Routes hold step DESCRIPTORS, not `Response` objects, so each call gets a fresh body: a stored `Response` is single-read and the readiness poll reads the same URL repeatedly. Global interceptors (MSW, nock, undici's `MockAgent`) are deliberately not used — all three patch globals, none can see a fetch passed as a function argument, MSW's `listen()` would silently overwrite the ENG-705 ban's `configurable` stub in every package, and a mock dispatcher would delete the `undici.Agent({ connect })` SSRF hook. (ENG-725)
- **core:** `makeSealedClientManager`, a new export on the existing `@manifest-network/manifest-mcp-core/__test-utils__/mocks.js` subpath (alongside `makeMockClientManager`) — a `CosmosClientManager` whose every method throws by name, so a REAL core broadcaster that escapes a test's mocks fails with a diagnostic instead of an unclassified `TypeError`. `ctx.chain` is the single seam every broadcast passes through (`cosmosTx(clientManager, ...)`, and `executeTx` reaches `ctx.chain.getBroadcastClient()` without importing `cosmosTx` at all), so sealing it contains the module-local `'../cosmos.js'` edge that no `vi.mock` of the core BARREL can reach — vitest does not rewrite intra-module references. `allow` opts individual methods back in; `SEALED_CHAIN_METHODS` is checked against `keyof CosmosClientManager` at compile time, so a new public method fails `npm run lint` rather than silently escaping the seal. (ENG-713)
- **fred, core, sdk:** readiness controls and typed provider-transport errors. `deploy_app` gains a `timeout_seconds` knob (1–1800, the one `wait_for_app_ready` already had); `PollOptions` gains `maxConsecutiveFailures`; `pollLeaseUntilReady` exports its `DEFAULT_POLL_TIMEOUT_MS` and `DEFAULT_MAX_CONSECUTIVE_FAILURES` and throws a typed `LeaseReadinessUnconfirmedError` (a `ProviderApiError` subclass carrying `reason: 'deadline' | 'provider_unreachable'`, the last state / provision_status seen, and the elapsed time). `ProviderApiError` gains an optional `kind` tag (`http` / `network` / `timeout` / `invalid_url` / `invalid_json` / `body_cap` / `poll`), `retryAfterMs`, and `cause`, since `status: 0` conflated seven unrelated causes and nothing could classify a provider failure without sniffing message text; `parseRetryAfterMs` and `isTransientProviderError` are exported alongside. New `ManifestMCPErrorCode.DEPLOY_READINESS_UNCONFIRMED` (non-retryable). All on the fred barrel and the SDK `/deploy` subpath. (ENG-661, ENG-479)
- **node:** every CLI gains an `export` subcommand (`manifest-mcp-chain export`, and so on) that prints the keyfile's 24-word recovery phrase after asking for its password. `keygen` now also displays the phrase it generates, once, with a write-it-down warning — the `gaiad keys add` norm. Before this, `keygen` printed only the derived address and there was no export path, so the encrypted keyfile plus its password was the sole copy of the seed; `export` is what recovers a mnemonic for wallets generated under that behaviour. The phrase is written to stderr with the prompts, so a plain `>` redirect does not capture it to disk. (ENG-668)

- **fred, core, sdk:** Fred's failure taxonomy. Fred's ENG-508 redacts the verbose `last_error` from tenant `/status`, `/provision` and `/releases` responses — it leaked host filesystem paths and raw exec output — and replaces it with a curated `reason` (stable machine-readable category) + `message` (short human summary) pair. `FredLeaseStatus` / `FredLeaseProvision` / `FredLeaseRelease` gain optional `reason` / `message`; `app_status`, `app_diagnostics` and `app_releases` surface them (sanitized for model context — previously `last_error` and the release `error` were forwarded raw); and `app_diagnostics` adds a derived `next_step` from a curated nine-row guidance table, which carries what the category code alone cannot: that `Internal` / `CleanupFailed` / `VolumeCleanupExhausted` are provider-side and unfixable by the tenant, and that `UpdateFailed` means the app is **still running the previous version** so a redeploy is the wrong advice. The taxonomy (`FRED_FAILURE_REASONS`, `FredFailureReason`, `isKnownFailureReason`, `describeFredFailure`, `failureDetail`, `FRED_REASON_GUIDANCE`, `guidanceFor`) is exported from the fred barrel and the SDK `/deploy` subpath as data, so a consumer can restyle the guidance without forking the taxonomy. `reason` is typed `string` and declared `z.string()` — never a closed union or `z.enum` — because Fred documents the set as open and add-only; an unrecognized value passes through verbatim and simply carries no `next_step`. (ENG-638)

- **fred, sdk:** one spelling for cancellation across the public surface. `LifecycleCallOptions` and `DeployCallOptions` now extend core's `CallOptions`, so they carry `signal` **and** `timeout` — the spelling core, agent-core, the agent MCP server and fred's own `waitForLeaseStatus` already used; `WaitForAppReadyOptions` gains `signal` (but not `timeout`, since its `timeoutMs` is already that call's deadline). The fred-only `abortSignal` is deprecated and still honoured: when both are supplied they are composed, so either one cancels. Each op resolves its effective signal exactly once, so a `timeout` cannot mint two independently-expiring deadlines. Additive — existing `abortSignal` callers are unaffected. (ENG-666)
- **fred, sdk:** `fetchJsonChecked` — fetch plus a bounded body read under ONE deadline, so `timeoutMs` is a budget for the whole call rather than for each phase separately. It is now the entry point for every provider read in the repo, and is exported on the fred barrel and the SDK `/deploy` subpath alongside `DEFAULT_FETCH_TIMEOUT_MS` and `BodyReadOptions`. Raw `checkedFetch` remains exported for the transport half, but it returns before the body is read — prefer `fetchJsonChecked` when calling the raw HTTP surface. (ENG-662)

### Changed

- **core, sdk:** `resolveCallSignal` now validates `CallOptions.timeout` and raises `INVALID_CONFIG` instead of letting the platform decide. `AbortSignal.timeout` is strict, so a bad value used to escape a helper documented as "merge two signals" as a raw Node `RangeError [ERR_OUT_OF_RANGE]` (`-1`, `1.5`, `NaN`, `Infinity`) or `TypeError [ERR_INVALID_ARG_TYPE]` (`'500'`). Worse were the values it *accepted*: Node takes the whole uint32 range, so anything from `2**31` to `2**32-1` threw nothing, emitted a `TimeoutOverflowWarning` to stderr, and silently became a **1 ms** deadline — a caller asking for ~25 days got an instant timeout. The accepted range is now an integer in `[1, 2147483647]`, the 32-bit timer ceiling, checked before any signal is minted so a throw cannot leak an armed, process-pinned timer, and before either seam does anything — a malformed deadline consumes no rate-limit token and sends no transaction. This is also why the check belongs in the library rather than the runtime: the `AbortSignal.timeout` IDL takes an `unsigned long long` with no `[EnforceRange]`, so a browser *coerces* where Node throws, and `core` builds `platform: "neutral"`. Also documented on `CallOptions.timeout`: the deadline covers the **whole** operation, so a retry ladder underneath inherits the already-elapsed budget; and composing `timeout` with `signal` pins the timeout signal plus its armed timer in a process-global strong set for the full duration regardless of when the call finishes (measured 0/300 collected once composed, vs 299/300 when not), so a lone `timeout` is the cheaper shape when caller cancellation is not needed. (ENG-710)
- **docs:** `docs/library-usage.md` no longer claims provider HTTP failures are auto-retried. Auto-retry (`withRetry` — 3 retries, 1s base, 10s cap) covers the **chain** query and tx paths; the provider path has none, deliberately, because several provider operations are non-idempotent — `checkedFetch` surfaces a `ProviderApiError` on the first non-2xx. The one tolerance that does exist, the readiness poll's consecutive-failure budget, is documented where the false claim used to be. `docs/troubleshooting.md` and the partial-success section gain the unconfirmed-vs-failed split, and the `deploy-app` MCP prompt no longer tells the model to offer `close_lease` on any `wait_for_app_ready` failure. (ENG-661)
- **fred:** the `diagnose-failing-app` MCP prompt now directs the model to `reason` / `message` / `next_step`, states the open-set rule (an unfamiliar value means fall back to `message`, not guess from the name), and warns that a non-empty `reason` records the *last* failure rather than current health. (ENG-638)
- **e2e:** the `submodules/fred` pin tracks Fred's unreleased `main` rather than a release tag, so the devnet exercises the post-ENG-508 wire contract before providers ship it. `e2e/docker-compose.yml` builds Fred from submodule source, so the gitlink is the e2e Fred version. (ENG-638)

### Fixed

- **core, fred:** core's cancellation seam no longer throws a reason that carries nothing, and the one blocking wait the SDK actually owns is now cancellable. Three defects, all reachable for the first time now that ENG-707 threads a real host signal into the lease tools. **(1)** `withReadSignal` threw `signal.reason` raw at three sites. That is the ENG-703 hole one package over, and the non-`Error` case is the *common* path rather than an edge case: the MCP SDK types the cancellation notification's `reason` as `z.string().optional()` and does `controller.abort(notification.params.reason)`, so when a client's own request timeout fires it cancels with `String(err)` and the thrown value is the bare string `McpError: MCP error -32001: Request timed out` — no `message`, no `stack`. All three sites now route through `abortReason`, which replaces only a reason carrying nothing at all (`null`, or `undefined` from a foreign/polyfilled signal) and passes an empty string through untouched, since that is a value the caller chose. The built-in `signal.throwIfAborted()` was deliberately **not** used for the two pre-checks the ticket suggested it for: it rethrows the reason raw, so `abort(null)` would still escape as `null` and render at the tool boundary as the literal message "null", leaving one file with two normalization rules. **(2)** `acquireRateLimit()` ignored the signal, so an abort landing during token contention was invisible until the token arrived — measured at t+3004ms for a cancel issued at t+100ms on a 3s limiter — and then still consumed a token it discarded. It now takes an optional `signal` (additive; every existing zero-argument call site and structural mock is unaffected) and, when given one, polls the synchronous `tryRemoveTokens` behind an abort-aware sleep. `limiter` exposes no cancellation and cannot be raced usefully — the abandoned `removeTokens` promise resolves later and takes the token anyway, and its own issue #33 is open with the internal timer id unreachable — whereas `tryRemoveTokens` consumes nothing when it declines, so a cancelled acquisition leaves the budget intact. That is the invariant Go's `x/time/rate` reaches by refunding a cancelled `Reservation`, without needing the refund. The no-signal path keeps `removeTokens` as its wait, so the ~20 call sites that pass no signal are timing-identical; measured equivalent regardless (4 sequential acquires at rps=2 take 1004ms either way). A `requestsPerSecond` below 1 — which `validateConfig` rejects but `getInstance` accepts, and `getInstance` is on the public SDK barrel — now raises `INVALID_CONFIG` on both paths instead of hanging the poll or surfacing a vendored library's wording. **(3)** `abortReason` and `abortableSleep` were hoisted out of fred into core and are exported from its barrel; fred imports both and its two copies are gone, collapsing three spellings of the same fallback into one. `abortableSleep` gains two deliberate deltas: a pre-aborted signal rejects the returned promise rather than throwing synchronously out of a promise-returning function, and a `null` reason is normalized on that leg too. The post-token re-check in `withReadSignal` is **kept**, not deleted as newly-redundant: `ctx` is taken structurally, so a hand-built ctx, a test double, or — under the caret peer range — an older core that ignores the new argument is gated by nothing else. Still unfixed, and not fixable here: the chain RPC itself takes no `AbortSignal`, so an abandoned read runs to completion (ENG-698). One knock-on worth recording, since it touches a guard rail: the SDK root-client size budget moves from 1.0761 MB to 1.0766 MB. The change adds 281 B gzip of first-party code to `CosmosClientManager`'s own graph, and the bump was taken only after confirming a trim cannot absorb it — gutting the timeout validator's error message entirely recovers 44 B and still breaches by 30 B, so the alternative was deleting the diagnostics this ticket exists to add, not reclaiming slack. That budget is a coarse floor-regression tripwire dominated by the ~1 MB cosmjs/manifestjs codegen floor; the real tree-shake guard is the `/reads` symbol-absence assertion in the browser-build test, and `/reads` and `/catalog` absorbed their ~160 B inside the existing budgets and are untouched. (ENG-710)
- **lease:** cancelling any of the 8 lease tools from an MCP host now stops the call, where all 8 previously ran to completion regardless. Every handler was declared `async (args) =>` and dropped the `extra` argument the SDK passes it, so no `signal` was ever built into the `CallOptions` bag and core's `withReadSignal` / `withTxConfirmation` always took their "no signal" fast path — the same class of dead-guard defect ENG-666 fixed in fred, here across an entire server rather than three tools. The fix is a dropped parameter restored: **no core signature changed and no export was added**, because all 8 core fns the tools call already take `opts` last and already forward it, and 3 of the 8 handlers were already *constructing* that object to pass `gasMultiplier`. Be precise about what this buys, because the phrase "cancellable" oversells it: manifestjs query methods accept **no** `AbortSignal`, so the RPC is not cancelled — you stop **awaiting** it, and the abandoned query runs to completion with its result discarded. What is genuinely guaranteed is what `withReadSignal` documents: an already-aborted call consumes neither a rate-limit token nor an RPC; the signal is re-checked after the (blocking) token wait, so a cancel arriving *during* rate limiting still prevents the query; the effective signal is resolved exactly **once**; and the losing read's rejection is swallowed with its abort listener removed, so there is no unhandled rejection and no listener leak. Only `signal` is threaded, never `timeout` — with a lone signal `resolveCallSignal` returns the caller's instance by reference, so the "two resolutions mint two independently-expiring deadlines" hazard is structurally impossible here rather than merely avoided by convention. On the three broadcasting tools (`fund_credit`, `close_lease`, `set_item_custom_domain`) the signal merges **into** the existing gas bag rather than replacing it, and `withTxConfirmation`'s existing contract applies unchanged: a cancel that lands before the broadcast sends **nothing**, while one landing after it stops the wait and reports `OPERATION_CANCELLED` with `details.sent: true` — the tx may still commit. Several legs remain deliberately unbounded and are **not** fixed here: `getQueryClient()`'s connect-retry, the `acquireRateLimit()` token wait itself, retry backoff, and `stopApp`'s own pre-broadcast and TOCTOU lease queries, which bypass `withReadSignal` and ignore `opts` entirely. Nor does this address the fact that abandoned reads hold their socket until the OS TCP timeout and accumulate **uncapped** under concurrent cancels — there is no fetch seam in core's query client to add one, it gets worse the more cancellation is used, and it is tracked in ENG-698. (ENG-707)
- **fred:** a provider call aborted by something other than its own deadline no longer fails with the message `undefined`. `classifyTransportError` opened on `err instanceof DOMException && err.name === 'AbortError'` and then returned `deadline.signal.reason` **without** checking `deadline.signal.aborted` — and `reason` is `undefined` on a signal that never aborted, so the thrown value was `undefined`: no message, no stack, nothing for a caller to branch on, and rendered at the tool boundary as the literal string `"undefined"`, since `withErrorHandling` stringifies a non-`Error`. Two paths reach that state on today's code. `fetchFn` is a public parameter (fred barrel, SDK `/deploy`), so a consumer whose own fetch wrapper enforces a shorter deadline rejects with an `AbortError` while ours never fired; and `timeoutMs <= 0` arms no timer of ours at all. Sniffing the error's shape was unreliable in the other direction too: an abort reason reaching this layer can be a `DOMException`, a plain string, an empty string or `null` (the MCP SDK aborts with `notification.params.reason`, an optional *string*), and a fetch stack may report **our** abort as something that is not a `DOMException`. Classification now keys on the two facts this module owns — `timedOut()`, then `signal.aborted`, then everything else — and never on the error, which is only read to render the network message and to carry `cause`. Two behaviour changes follow, both deliberate. A **non-abort** error arriving after our own timer fired is now `kind: 'timeout'` rather than `kind: 'network'`: we killed the request, so the fetch stack's choice of error object is not evidence about the cause — retryability is unchanged either way, and the original error is preserved, because the timeout error now carries `cause`. And an abort raised **below** us is now a retryable `kind: 'network'` instead of failing the call outright, since its realistic provenance is a shorter deadline elsewhere or a stream reset — the same transient family as a connect error, bounded by the readiness poll's consecutive-failure budget. A **cancellation is unchanged, and stays deliberately unwrapped**: the caller's own reason is surfaced verbatim, so it is not a `ProviderApiError` and `isTransientProviderError` rejects it for free — a user's cancel cannot be retried by construction, and consumers keep recognising one by `signal.aborted` rather than by the error's shape, which is what the standard requires of an API that composes a caller's signal and what the poll's own catch already assumed. The only reasons replaced are those carrying nothing at all (`null`, or `undefined` from a foreign signal); an empty string is a value the caller chose and is carried through. The same nullish hole is closed at the file's two sibling abort-surfacing sites through one shared helper. No public surface change. (ENG-703)
- **fred, core:** provider-controlled text and release manifests no longer reach model context with no length bound. Two paths. **Error bodies:** `checkedFetch` turned a non-2xx body into the `ProviderApiError` message with only the 10 MiB *transport* cap applied, and `withErrorHandling` copied that message verbatim into the tool's error response — `sanitizeForLogging` redacts secrets but never truncates. Bounded at three layers, each with a distinct job: the `ProviderApiError` **constructor** caps at 4096 code points, which makes the invariant total across all ten construction sites, both subclasses, and two sinks a call-site cap would miss (the readiness prose that embeds a nested error, and `browse_catalog`, which reports a per-provider `healthError` in a *success* response); the nested excerpt inside that prose is capped tighter at 256, so a long inner error cannot push the load-bearing "this is NOT a reported failure" sentence past the outer cap and delete it; and `withErrorHandling` caps at 2000 on the way into the tool response — but **only** in its non-`ManifestMCPError` branch, because first-party messages are curated recovery guidance whose length is a reviewed design choice. stderr keeps the full message on every path: it is not model context, so there is no diagnostic loss. **Release manifests:** `app_releases` spread each release wholesale into `structuredContent`, and Fred's `ReleaseInfo` carries the full base64 manifest for every release (`Manifest []byte` with no `omitempty`, so it is always present) — which `structuredResponse` then duplicated into the text content, landing it in context twice. The blob is dropped and only its size reported, as `manifest_bytes`, computed without decoding; a model cannot usefully decode base64, and no MCP tool returns a historical manifest body anyway — the raw bytes stay on the library `getLeaseReleases` path. Release *count* was a second unbounded dimension — neither side paginates and Fred prunes by age, never by count, while `restart_app` appends a release too — so the 20 most recent are returned with `release_count` and `truncated`. The transport layer bounds length only; character sanitization stays at the tool layer, since a `ProviderApiError` message is also an SDK value and a stderr line where collapsing newlines would destroy structure. (ENG-669)
- **fred, agent-core:** cancelling `restart_app`, `restore_app` or `update_app` from an MCP host now actually stops the work, and a cancelled restore no longer leaves the user paying for a lease they never got. Only `deploy_app` and `wait_for_app_ready` took the MCP `extra` argument; the other three handlers were declared `async (args) =>` and dropped it, so `abortSignal` was always `undefined` and **every** abort guard inside `restartApp` / `restoreApp` / `updateApp` was unreachable code. The guards were correct and unit-tested — they were simply never fed a signal from the one surface that needed them. `restore_app` made this sharp: ENG-488 put a `throwIfAborted()` immediately before its non-idempotent, credit-reserving create-lease broadcast precisely so a cancel during the slow pre-flight reads could not reserve credit, and on the MCP path that guard could never fire. The three handlers now thread `extra.signal`, which the SDK aborts on host cancellation, on the client's request timeout, **and** on transport close. Fixing that exposed the second half: an abort landing *after* the create-lease broadcast re-threw a bare `AbortError` naming no lease and writing no log line, leaving a credit-reserving PENDING shell behind — and because a cancelled MCP request receives no response at all, the uuid would not have reached the user even if the error had carried it. At that point the restore POST provably has not fired, so nothing is adopted and the lease is the same empty shell the uncommitted-terminal branch already rolls back; it is now rolled back the same way, reported as `OPERATION_CANCELLED` with `details.lease_uuid` and `rolled_back: true`, and falls through to the existing orphan surface if the compensating cancel itself fails. The old `if (aborted) throw err` bypass in the restore-POST catch is removed: it made side-effect classification depend on whether the caller happened to cancel, so a genuine provider rejection that merely coincided with a cancel suppressed both the rollback and the orphan record. Classification now depends on the provider's answer alone. Separately, `agent-core`'s orchestrated deploy passed no signal to its `needs_wait` readiness poll — often the longest leg of the flow — though the same function already forwarded one to the deploy leg. (ENG-666)
- **fred:** a provider that returns headers promptly and then trickles the response body can no longer pin a tool call open forever. `checkedFetch` composed the caller's `AbortSignal` with a 30s timeout, but its `finally` cleared the timer and detached the caller's abort listener **before** any body was read — so every body read ran with no deadline and an orphaned signal. Both sides of that `finally` were exposed: the `!res.ok` error-body read inside `checkedFetch` itself, and the `Response` handed back on the success path for the caller to read. undici's 300s inactivity backstop is defeated by any trickle above zero bytes, so neither the timeout nor an MCP host's cancellation could terminate the call; the 10 MiB cap bounds memory, not time. Provider `apiUrl`s come from on-chain SKU records, so the endpoint is attacker-influenced — the same trust boundary as the SSRF work. The composed deadline is now a first-class object whose window extends over the error-body read, and `readBodyCapped` arms its own deadline whenever a caller does not supply one, so a body read through `readBodyCapped` / `parseJsonResponse` — including `checkedFetch`'s success path and the no-stream `res.text()` fallback (bounded by racing, since there is no reader to cancel) — is covered by default rather than by remembering to opt in. Reading a raw `checkedFetch` Response with `res.text()` / `res.json()` directly still bypasses both caps; `fetchJsonChecked` is the bounded entry point, and is what every provider read in this repo now uses. A stall/inactivity deadline was deliberately rejected — one byte every `N-1`ms survives it forever; only a total budget bounds a hostile trickle. The composition stays hand-rolled rather than `AbortSignal.any` + `AbortSignal.timeout` because it must *disarm* the timeout when the caller aborts first, so a delayed rejection is never misclassified as a timeout. A body-phase timeout reuses `kind: 'timeout'` and keeps the response's `status` and `retryAfterMs`; a caller cancel mid-body surfaces the caller's own reason rather than being laundered into placeholder body text, which the readiness poll depends on. (ENG-662)
- **node:** a **pasted** password or mnemonic is no longer silently corrupted. The hidden-input reader put stdin in raw mode and treated each `'data'` event as one keystroke, but a terminal delivers a paste as a single chunk: every terminator comparison missed, and the catch-all `ch >= ' '` branch — a lexicographic comparison on the chunk's *first* character — appended the whole string, embedded CR/LF included, to the secret. Pasting a password copied with a trailing newline encrypted the keyfile under `pw\r\n` while the user believed it was `pw`, and the confirm prompt matched because the same paste was repeated; the mismatch only surfaced later, when `MANIFEST_KEY_PASSWORD` failed to decrypt. Combined with `keygen` never revealing the mnemonic, that was unrecoverable loss of any funds at the address, with no error at the time it happened. Chunks are now folded character by character (by code point, so a backspace cannot split a surrogate pair): a terminator ends the read and anything after it *in the same chunk* is discarded, and stray C0 controls are dropped rather than absorbed. The classification is a pure, exported function with unit coverage — the previous shape had none at all, which is why a wallet-corruption path lived in it. If you already hold a keyfile you cannot open, see the decryption entry in `docs/troubleshooting.md`: it is likely encrypted under the exact bytes `yourpassword\r\n`, and `export` will then recover the mnemonic. (ENG-668)
- **core:** an explicit `fee` or `memo` passed to `cosmos_tx` (and the SDK `/chain` escape hatch's `cosmosTx`) is no longer discarded for 13 of the 14 tx modules, and no longer switches the `COSMOS_MAX_GAS` ceiling off. `cosmosTx` forwards `txExtras` as the eighth argument to the registered handler, but only `routeBillingTransaction` declared a parameter to receive it — the other thirteen declared six. A JS call with more arguments than the callee declares is legal, and `TxHandler` marks the trailing params optional, so the value was dropped in total silence. Worse, `cosmos.ts` deliberately skips building `TxOptions` whenever an explicit fee is supplied (the fee is meant to win), so those handlers then called `buildGasFee` with no options, which returns `'auto'`. The single code path where a caller states a fee explicitly — i.e. where they are being *most* careful about cost — was therefore the one path that discarded that fee, signed with a fee they never authorised, and handed gas estimation back to an unbounded `'auto'`, bypassing the ENG-556 ceiling that exists to bound what a hostile or compromised RPC can make the wallet pay. The fee/memo resolution is now a single shared `resolveTxFeeAndMemo` helper that every one of the fourteen routes calls (including billing, whose inline copy was the original), and the ceiling is enforced against an explicit fee in `cosmosTx` before dispatch, so it covers every module. Guarded three independent ways, each derived rather than hand-listed: the registry's own accessor asserts every registered handler declares all eight parameters, a source scan asserts every route file resolves through the shared helper and none calls `buildGasFee` directly, and behavioural tests assert the supplied fee and memo reach the signed transaction. Reverting a single handler to its pre-fix shape fails all three. Both ceiling checks (simulated and explicit-fee) resolve their bound through one shared helper, so an omitted `maxGas` falls back to `DEFAULT_MAX_GAS` on both paths and a malformed one (`0`, `-2`) is rejected rather than silently treated as disabled — only `-1` disables. (ENG-665)
- **core:** a query against an unreachable or degraded RPC no longer amplifies into 77 connection attempts. `cosmos.ts` acquired the client *inside* its own `withRetry` — deliberately, so a failure there carried `{module, subcommand}` attribution — while `getQueryClient`/`getSigningClient` retry the connect internally and the RPC branch builds five namespace clients per attempt. The two ladders multiplied: 4 outer × 4 inner × 5 sockets. The nesting had been latent since both ladders were written, suppressed by the very bug ENG-636 fixed — a rejected init promise that latched forever made outer attempts 2-4 re-await the cached rejection instantly, so the inner ladder ran exactly once. Un-latching it correctly exposed the amplification: measured 20 connects / ~14s → 77 / ~35s, and a second query on the same manager 6.4s → 31.9s, which timed out `e2e/retry.e2e.test.ts` on the nightly. The cost is not only CI: against an RPC that is degraded rather than dead, the same multiplication scales with connect latency and can exceed the MCP SDK's 60s request timeout, so the caller sees an opaque cancellation instead of `RPC_CONNECTION_FAILED`. Client acquisition is now hoisted out of every call-site ladder (`cosmosQuery`, `cosmosTx`'s context-load and broadcast legs, `cosmosEstimateFee`, `executeTx`) into its own try/catch that preserves the same attribution, leaving connect-retry with a single owner; the broadcast paths acquire inside `withBroadcastLock` but outside the ladder, so serialization is unchanged. The rate-limit token stays inside the ladder — it is a request budget, not a connection budget. Behaviour is otherwise preserved, including the `superseded` init error, which the outer ladder never retried anyway (its message matches no transient pattern). Guarded by unit tests that pin the acquisition count under a real retry ladder, and by an elapsed-time upper bound in the e2e test whose budget and header comment now match the measured reality. (ENG-679)
- **fred, core, agent-core, sdk:** `deploy_app` no longer reports a healthy, still-provisioning, already-paid-for lease as a failed deploy and point the agent at a tool that would tear it down. Three defects composed on one code path. The readiness poll used a 120s default while Fred's docker backend allows **10 minutes** to provision — 5 of them for the image pull alone — so any cold pull past ~2 minutes tripped the deadline on a lease that was fine, and `deploy_app` exposed no knob to raise it; the default is now the provider's own ceiling (`DEFAULT_POLL_TIMEOUT_MS`, 600s) and `timeout_seconds` is exposed. The in-loop status read had **no try/catch and no failure budget**, so one 502 from a provider's ingress, one DNS blip, or the 404 window right after create-lease while the provider ingests the new lease aborted the whole deploy — roughly 40 chances to fail per deploy against a third-party endpoint; it now tolerates `maxConsecutiveFailures` consecutive read failures (default 3, reset on every success) and honours a `Retry-After` header, which `checkedFetch` previously discarded even though Fred sends one with every 429. A status-read **404 is tolerated inside this poll specifically** — that is the ingestion window, and it stays a hard error on every other provider call. Only the status READ is inside the new try: chain-state checks, auth-token minting, terminal lease states and a `PROVISION_FAILED` verdict all sit outside it and can never be swallowed. And every post-create-lease failure was rewritten as *"Deploy partially succeeded: … Close this lease with `close_lease` if needed"* — including a readiness timeout, i.e. a false **failure** recommending destruction, the mirror image of ENG-651's false success. Once the poll has started, the ONLY thing that now justifies "the deployment failed" is the provider saying so — a `PROVISION_FAILED` status, a terminal lease state, or a state this client cannot interpret, all tagged `poll_verdict`. Everything else at that step is silence, not a verdict (deadline, 401/404, oversized body, auth-token mint failure, caller cancel), and reports **unconfirmed rather than failed**: the message says the lease is live and may still be starting, points at `app_status` / `wait_for_app_ready`, and says to close it only once the provider reports a failed `provision_status`. Defaulting to unconfirmed and carving out the verdict — rather than the reverse — means a fault nobody anticipated reads as "we do not know", which is recoverable, instead of "it failed", which invites destruction. The `Deploy partially succeeded:` prefix and `details.partial === true` are kept on every branch so the ENG-280 classifier contract is unchanged; the unconfirmed branch adds `details.readiness_unconfirmed`, `poll_reason`, `last_state` and `last_provision_status`. The set-domain and upload branches keep the original wording verbatim — there, nothing is running and `close_lease` really is the remedy. (ENG-661, ENG-479)
- **agent-core:** the orchestrated deploy path carried the same defect, and one more. `DeployAppOptions.waitForReadyTimeoutMs` never reached fred's internal readiness poll — it governed only the follow-up `wait_for_app_ready` on the `needs_wait` branch, so the cold-start wait, where the minutes actually go, ran on fred's default and was unreachable from the API; it now threads through to both. A readiness timeout out of `waitForAppReady` was reported as `TX_FAILED` ("wait_for_app_ready failed for lease X") with no recovery prompt at all, and now surfaces `DEPLOY_READINESS_UNCONFIRMED`. And the recovery prompt selected its body by *whether a custom domain was requested*, a proxy for "the set-domain step failed" that is wrong whenever the deploy got past it: since set-domain runs first, a domain-carrying deploy whose readiness poll timed out was told the domain never landed and the manifest was never uploaded — both false — and offered `retry_set_domain` for a domain already claimed. The prompt now selects on the reported step, falling back to the old inference for fred builds that send neither flag. Only the explicit `readiness_unconfirmed` flag may claim "not a reported failure": `failedStep: 'poll'` alone must not, because fred reports that step for a provider verdict too, and softening a confirmed failure into "may still be coming up" would be this bug's exact inverse. A verdict at the poll step now renders as one. (ENG-661)
- **core:** `isRetryableError` no longer treats a partial success as retryable. `details.partial === true` means a lease already exists on-chain and is being billed, and `deploy_app` is non-idempotent — a retry buys a second paid lease. The readiness-timeout wrap preserved the inner `QUERY_FAILED` code and its message contains "timed out", which the transient-message sniff matched. Latent (nothing wraps the deploy path in `withRetry` today) but closed alongside the work that makes provider errors classifiable. (ENG-661)
- **fred, sdk:** `waitForLeaseStatus` no longer reports a **retained** lease — one the provider tore down while keeping its volumes — as a successful deploy. Three things composed: Fred publishes `provision_status: "retained"` from a deprovision callback; the `/events` frame carries a provision status but **no chain state**, so the WebSocket mapping pinned `LEASE_STATE_ACTIVE`; and the ACTIVE branch treated any status outside `PROVISION_FAILED` / `PROVISION_IN_PROGRESS` as ready. A consumer waiting on a deploy got a success-shaped `FredLeaseStatus` for a lease that was closed, billing-dead and recoverable only inside an expiring grace window, and `isLeaseFailureTerminal` returned `false`, so the standard failure check missed it too. Two changes, either of which would have prevented it. **Readiness is now an allowlist** (`PROVISION_SUCCESS`, i.e. `ready`): a populated status this client does not recognize keeps the wait running and is logged once, instead of being reported as healthy — an absent field still resolves, since that is a provider which never populates it rather than an unrecognized value. And **a WebSocket frame is now a trigger, not data**: a frame that could settle the wait causes an authoritative `GET /status`, and the provider's own document is what gets classified, so the two transports cannot disagree about the same lease. The one asymmetry is deliberate — a `PROVISION_FAILED` frame whose read fails still resolves from the frame, because a terminal-negative signal is self-sufficient, while a success-shaped one is not. This also corrects the poll path, where `ACTIVE + retained` was the same false success: it is reachable because Fred emits the retained notice from a branch that leaves chain state untouched, and it is **not** terminal there — the provider's reconciler re-provisions an ACTIVE lease it finds unprovisioned, so the wait correctly keeps waiting rather than failing. `PROVISION_SUCCESS` joins its two sibling sets on the fred barrel and the SDK `/deploy` subpath. (ENG-651)
- **fred, core:** mono no longer goes dark against a post-ENG-508 provider. Type declarations modelled only the removed `last_error` / `error` and nothing read the replacements, so `app_diagnostics` would have reported a failure with no cause and `pollLeaseUntilReady` — the only channel carrying Fred failure detail into the deploy flows and agent-core — would have lost its diagnosis entirely, silently, with the whole test suite green (every fixture mocked the old shape). Both wire shapes are now read, preferring `reason` / `message` and falling back to the deprecated fields, since providers upgrade independently of this client. The deprecated fields are retained rather than removed, so the published SDK type change is additive. The `/events` WebSocket frame is unchanged by ENG-508 and still carries `error`; verified that its value is Fred's `callback.Error` — the same string Fred assigns to `ProvisionState.Message` — so it now maps to the canonical `message`, with `last_error` kept one release as a deprecated mirror. (ENG-638)
- **core:** `CosmosClientManager` no longer caches a rejected init promise forever. Both lazy-init paths captured their own promise inside an `async` IIFE's *synchronous* prologue — i.e. before the assignment landed — so the capture was always `null` and every identity guard was permanently false. One transient RPC failure latched a rejected promise that every later caller re-awaited: a permanent outage for a long-running MCP server until process restart. The init bodies now live in separate `initQueryClient`/`initSigningClient` methods with the cache bookkeeping in chained `.then` handlers, so the guard compares against the promise actually stored. Three consequences come alive with it: the resolved client is promoted to the object cache (`getInstance`'s config-change eviction and `teardown`'s disconnect were both unreachable before, so the manager never disconnected a signing client), a successful signing init no longer calls `disconnect()` on the client it returns (inert only because `@cosmjs/tendermint-rpc`'s `HttpClient.disconnect()` is a no-op — a WebSocket endpoint would have been closed the instant it was created), and an init genuinely superseded mid-flight by a disconnect or config change now releases the orphaned signing client and fails its caller with `RPC_CONNECTION_FAILED` + `details.reason: 'superseded'` instead of handing back a disconnected client. Adds the retry-after-failure and supersede tests that were previously omitted with an incorrect rationale. (ENG-636)

### Upgrade notes

- **Behaviour change (`CallOptions.timeout` is validated):** a `timeout` that is not an integer in `[1, 2147483647]` ms now throws `ManifestMCPError(INVALID_CONFIG)` from `resolveCallSignal` — and therefore from any read, transaction or orchestrated call it is passed to — before the call does anything. Most rejected values already failed, just less legibly (Node threw a raw `RangeError`/`TypeError`), so the genuinely new rejections are three: **`timeout: 0`**, which used to mint a deadline that fired on the next macrotask, so the operation never ran and the caller got a bare `TimeoutError` with nothing to explain it; and anything from **`2**31` to `2**32-1`**, which used to be accepted and silently downgraded to a **1 ms** deadline. If you compute a deadline by subtraction (`deadline - Date.now()`), clamp it to at least 1 and handle "already expired" yourself — an already-aborted `signal` is the honest way to express that. No in-repo caller passed an affected value. (ENG-710)
- **Behaviour change (cancelling a rate-limited read):** a cancelled call now surfaces during the rate-limit wait rather than after it, and gives its token back. If you cancel a read that is queued behind the client-side rate limiter, it rejects immediately instead of waiting out the token — so a caller that previously observed a cancel only once the token arrived (up to a full limiter interval later) now observes it at once, and the token stays available for the next request. The rejection carries the caller's own abort reason, unwrapped, matching the rest of the read path. Callers passing no `signal` are unaffected in every respect, including timing. Separately, a `rateLimit.requestsPerSecond` below 1 — always invalid, and rejected by `validateConfig`, but accepted by `CosmosClientManager.getInstance`, which does not validate — now fails fast with `INVALID_CONFIG` on the first acquisition instead of surfacing `limiter`'s own `Requested tokens 1 exceeds maximum tokens per interval` wording. (ENG-710)
- **Behaviour change (lease-tool cancellation):** all 8 lease tools — `credit_balance`, `fund_credit`, `leases_by_tenant`, `close_lease`, `set_item_custom_domain`, `lease_by_custom_domain`, `get_skus`, `get_providers` — now abort on a host cancel, on the MCP client's request timeout (**60s by default** in the TypeScript SDK), and on transport close. They previously ignored all three and ran to completion, so a call that used to finish server-side will now be aborted if your client's request timeout is shorter than the call takes — raise the client timeout rather than relying on the old behaviour. For the three broadcasting tools this is a change in *outcome*, not just in timing: a cancel arriving before the broadcast means **no transaction is sent**, but one arriving after it rejects with `OPERATION_CANCELLED` carrying `details.sent: true`, and the transaction **may still commit on-chain** — treat that outcome as unknown and re-query the chain rather than blindly retrying (`OPERATION_CANCELLED` is non-retryable, so the retry layer will not re-broadcast for you). A cancelled **read** rejects with the raw abort reason rather than a `ManifestMCPError` — deliberately, since rejecting with the signal's own reason is what the DOM standard asks of an API that accepts an `AbortSignal`, and it is what every other core read consumer already does. Two consequences for callers. It surfaces at the tool boundary under `code: 'UNKNOWN'`, because `withErrorHandling` only recognizes a `ManifestMCPError` code. And the reason **need not be an `Error`** — in the most common case it is not. The MCP SDK aborts with the cancellation notification's `reason`, which is an optional *string*, and the standard substitutes an `AbortError` `DOMException` only when the aborter passes nothing. When the MCP **client's own request timeout** fires it cancels with `reason: String(err)`, so the value thrown is the plain string `McpError: MCP error -32001: Request timed out` — a string, with no `message` and no `stack`. Detect cancellation from `signal.aborted`, never from the error's shape or its message. (The tx path differs on purpose: it wraps into `OPERATION_CANCELLED` and keeps the original under `details.reason`, which is the convention Node's own promise APIs follow.) (ENG-707)
- **Behaviour change (`app_releases` output shape):** `structuredContent` no longer carries `manifest` on a release element, and gains `manifest_bytes` (per element) plus `release_count` and `truncated` (top level). Only the 20 most recent releases are returned. No MCP tool returns a historical manifest body (`build_manifest_preview` only builds and validates a candidate the caller supplies). A consumer that needs the raw bytes should read the library path, where `getLeaseReleases` and `FredLeaseRelease.manifest` are deliberately **unchanged** — the cap is an AI-context bound, not a wire change. (ENG-669)
- **Behaviour change (error-message length):** an error message mono did not author — a provider response body, a third-party library error — is truncated to 2000 code points in the tool response, with an appended `…`. First-party `ManifestMCPError` messages are unaffected, and stderr still receives the full text. A consumer parsing provider error bodies out of a tool response should not assume the whole body is present. (ENG-669)
- **Behaviour change (lifecycle-tool cancellation):** `restart_app`, `restore_app` and `update_app` are now genuinely cancellable. They previously ran to completion regardless; they now abort on a host cancel, on the MCP client's request timeout (**60s by default** in the TypeScript SDK), and on transport close. If your client's request timeout is shorter than one of these operations takes, calls that used to complete server-side will now be aborted — raise the client timeout rather than relying on the old behaviour. The abort still takes effect *before* the mutate POST or *during* the readiness poll; an in-flight non-idempotent POST is deliberately not interrupted, because it cannot be safely un-sent. (ENG-666)
- **Behaviour change (cancel before the deploy broadcast):** `deployApp` / `deployManifest` now check the signal immediately before the credit-reserving create-lease broadcast, matching the guard `restoreApp` has had since ENG-488. A deploy cancelled — or timed out, now that `timeout` is supported — during SKU/provider resolution therefore creates **no lease**, where it previously broadcast first and observed the cancellation only afterwards. `onLeaseCreated` consequently does not fire in that case; when the abort lands after the broadcast it still fires, as before. (ENG-666)
- **Behaviour change (cancelled readiness wait):** in `agent-core`, cancelling the orchestrated deploy's `needs_wait` readiness poll now rejects with `OPERATION_CANCELLED` + `details.partial`/`lease_uuid` instead of `TX_FAILED`. The lease exists and the manifest is uploaded, so reporting a failed transaction was actively misleading — the same correction ENG-661 made for the readiness-timeout branch. (ENG-666)
- **Behaviour change (cancelled restore rolls back):** a `restore_app` cancelled after its create-lease broadcast now issues a compensating `billing cancel-lease` and rejects with `OPERATION_CANCELLED` (`details.lease_uuid`, `details.rolled_back: true`), where it previously re-threw a bare `AbortError` and left the lease reserving credit. A cancel *before* the broadcast is unchanged — it still has zero side effects. If the compensating cancel fails, the outcome is the existing `RESTORE_ORPHAN_COMPENSATION_FAILED` with `details.orphaned_lease_uuid`. Both outcomes emit a single-line JSON stderr record (`restore_aborted` / `restore_orphan`) for alerting. (ENG-666)
- **Behaviour change (provider-call deadlines):** `timeoutMs` now covers the response **body** as well as the headers. Two visible consequences. `getProviderHealth`'s 5s is now a whole-call budget — previously a stalled body could extend it to 5s + 30s. And a non-2xx whose body stalls now reports `kind: 'timeout'` (transient) instead of `'http'`, since the body was never seen; `status` and `retryAfterMs` are preserved, so status-based branching (including the readiness poll's 404 tolerance) is unaffected. A direct `readBodyCapped` / `parseJsonResponse` caller that wants no deadline can pass `{ timeoutMs: 0 }`. (ENG-662)

- **Behaviour change (readiness deadline):** `pollLeaseUntilReady` now defaults to **600s** instead of 120s, and so do its callers when given no explicit `timeoutMs` — `waitForAppReady` / `wait_for_app_ready`, `deployApp` / `deploy_app`, and the library paths of `restartApp` / `updateApp` / `restoreApp`. A deploy that is genuinely stuck therefore takes up to 10 minutes to report, matching how long the provider is actually allowed to take. Override per call with `pollOptions.timeoutMs` (library) or `timeout_seconds` (MCP; the cap rose from 600 to 1800 so the knob can still exceed the default). Two things to check in your own code: an MCP client's request timeout must exceed the tool's deadline or it will cancel first (the SDK default is 60s), and a test harness's per-test timeout must exceed both. `waitForLeaseStatus` keeps its own separate 120s default — it is a general terminal-state watcher, not the deploy readiness path. (ENG-661)
- **Behaviour change (poll fault tolerance):** the readiness poll now tolerates 3 consecutive provider status-read failures before giving up; pass `maxConsecutiveFailures: 0` for the previous fail-on-first-error behaviour. Two consequences: a transient fault costs one extra interval instead of failing the call, and a provider unreachable for the *whole* window now rejects with `LeaseReadinessUnconfirmedError` (`reason: 'provider_unreachable'`, the transport error on `cause` and in the message) rather than that transport error directly. Non-transient failures — 4xx other than 429 and 404, SSRF/URL rejections, body-cap breaches, and anything that is not a `ProviderApiError` — still propagate on the first occurrence. The 404 exception is scoped to the readiness poll (the post-create-lease ingestion window) and is bounded by the same budget; a 404 from any other provider call is unchanged. (ENG-661, ENG-479)
- **Behaviour change (deploy partial-success errors):** a deploy whose readiness poll times out is now coded `DEPLOY_READINESS_UNCONFIRMED` (was `QUERY_FAILED`) and no longer says "Close this lease with `close_lease` if needed". The `Deploy partially succeeded:` prefix and `details.partial === true` are unchanged on every branch, so `classifyDeployError`-style consumers are unaffected; branch on `details.readiness_unconfirmed === true` for the finer split. A caller that matched the old advice text to drive cleanup should switch to the flag — and reconsider closing on this signal at all, since the lease may be hosting a healthy app. (ENG-661)
- **Behaviour change (lease-status waiters):** an ACTIVE lease whose `provision_status` this client does not recognize is no longer reported as ready. `waitForLeaseStatus` keeps waiting (and rejects on its deadline naming the last status seen) and `pollLeaseUntilReady` keeps polling, where both previously returned success. Against the provider's current status set the only value affected is `retained` — every other value was already classified — so in practice this changes a false success into a correct one; the broader rule exists so the *next* status a provider adds cannot reproduce the bug. If you deliberately relied on unrecognized-means-ready, gate on `PROVISION_SUCCESS` (now exported from the fred barrel and SDK `/deploy`) explicitly instead. (ENG-651)

- Refactor(billing): align all custom-domain input-validation throws on `INVALID_CONFIG` so the same logical issue (empty / whitespace `custom_domain`, mutual exclusion, malformed `service_name`, mutually-exclusive `--clear-*` + values) produces the same error code regardless of whether the input arrives via `set_item_custom_domain`, `lease_by_custom_domain`, `cosmos_tx billing set-item-custom-domain`, `cosmos_query billing lease-by-custom-domain`, the `setItemCustomDomain` core helper, or `deploy_app`'s eager pre-flight. Both `INVALID_CONFIG` and the previously-used `TX_FAILED` are non-retryable, so retry behaviour is unchanged. Chain-side rejections (the actual `MsgSetItemCustomDomain` / `Query/LeaseByCustomDomain` failures, including the keeper's `NotFound` for an unclaimed FQDN) keep their existing codes (`TX_FAILED` / `QUERY_FAILED`) — those classify "the chain answered no", not "your input was bad".
- Feat(fred): `deploy_app` accepts an optional `custom_domain` (and `service_name` for stack leases) so a tenant can claim an FQDN in the same call that creates the lease. The set-domain tx is submitted between create-lease and the manifest upload — providerd has the domain available when it provisions. Failures slot into the existing partial-success error wrap (`Deploy partially succeeded: lease X was created but subsequent steps failed. Close this lease with close_lease if needed.`), so callers don't see a new error shape per failure mode. Input validation (empty / whitespace-only domain, missing or mismatched `service_name` on a stack lease, stray `service_name` on a single-item lease) fires before any chain tx so a misconfigured deploy doesn't leave a paid-for lease behind.
- Feat(lease): add `set_item_custom_domain` MCP tool that sets or clears the FQDN on a lease item via `MsgSetItemCustomDomain` (manifestjs 2.4.1 / manifest-ledger v2.1.0). Pass `custom_domain` to set, or `clear: true` to remove. Optional `service_name` addresses the LeaseItem inside a stack lease; omit for a 1-item legacy lease. Authorised signers are the lease tenant, the module authority, or any address in `params.allowed_list`. Annotated as non-destructive + idempotent (re-setting the same value is a no-op).
- Feat(lease): add `lease_by_custom_domain` MCP tool — reverse-lookup the active or pending lease that has claimed a given FQDN; returns the lease and the `service_name` of the item holding the domain (empty string for legacy 1-item leases).
- Feat(lease): `leases_by_tenant` per-item output now surfaces `serviceName` and `customDomain` so callers can see which lease item owns a domain without a second query.
- Feat(core/billing): add `lease-by-custom-domain` query subcommand and `set-item-custom-domain` transaction subcommand to the generic `cosmos_query` / `cosmos_tx` surface. New `--service-name <name>` flag selects the LeaseItem inside a stack lease; `--clear` clears the existing domain.
- Feat(core/billing): `update-params` now preserves the on-chain `allowed_list` and `reserved_domain_suffixes` by default. Before broadcast, `cosmosTx` reads the current `Params` and threads them as a `TxBuildContext` so the message-builder fills in any list field the caller did not explicitly override. Pass `--reserved-suffix <.example.com>` (repeatable) or trailing positional `<allowed-address>...` to overwrite a list; pass `--clear-reserved-suffixes` or `--clear-allowed-list` to explicitly empty one. Mixing positional addresses with `--clear-allowed-list`, or `--reserved-suffix` with `--clear-reserved-suffixes`, is rejected with a structured `INVALID_CONFIG`. The previous behaviour silently cleared whichever list the caller did not enumerate, since `MsgUpdateParams` overwrites the full `Params` struct.
- Feat(core): add `TxBuildContext` type and an optional 7th `context` parameter to `TxHandler` / 4th to `TxMsgBuilder`. Existing handlers ignore it; `routeBillingTransaction` consumes `context.currentBillingParams` to drive the preserve-by-default behaviour above. `cosmosTx` and `cosmosEstimateFee` look up an optional `TxBuildContextLoader` in the per-module `TX_MODULES.contextLoaders` registry and run it before dispatching, so each handler that needs chain state declares its own loader inline (`loadBillingUpdateParamsContext` is the first). The dispatcher acquires a rate-limit token before the loader runs and wraps non-`ManifestMCPError` failures as `QUERY_FAILED` with `{module, subcommand}` details, so broadcast and estimate paths see symmetric error classification. Subcommands without a loader pay no extra round-trip.
- Feat(core): export `setItemCustomDomain` helper (mirrors `stopApp` / `fundCredits`) and `LeaseByCustomDomainResult` type.
- Test(e2e): add `e2e/billing-custom-domain.e2e.test.ts` covering set/lookup/clear via both the lease MCP tools (`set_item_custom_domain`, `lease_by_custom_domain`, `leases_by_tenant`) and the generic chain layer (`cosmos_tx billing set-item-custom-domain`, `cosmos_query billing lease-by-custom-domain`) against the local devnet, plus chain-side and client-side rejection paths.
- Chore(e2e): bump the `submodules/manifest-ledger` pin from the `fmorency/manifest-ledger` fork (`billing-v2` @ `0031210`) to upstream `manifest-network/manifest-ledger` (`v2.1.0` / `0319a7c`). Required to ship the chain image with `MsgSetItemCustomDomain` and `Query/LeaseByCustomDomain` registered — manifestjs 2.4.1 was generated from upstream v2.1.0, so the chain proto types must match. `e2e/billing-custom-domain.e2e.test.ts` probes for the new query in `beforeAll` and skips gracefully on older chains.
- Chore(deps): bump `@manifest-network/manifestjs` to 2.4.1

## [0.7.0] - 2026-04-30

- Fix(fred): `FredLeaseProvision.last_error` is now declared optional in the public TypeScript interface, matching the runtime behavior the M1 outputSchema fix already reflects. Removes an unsafe `undefined as unknown as string` cast from the regression test (ENG-87).
- Fix(fred): `app_diagnostics` outputSchema declares `last_error` as optional. The Fred provider omits the field when there's no recent failure, so the M1 schema (`last_error: z.string()`) was rejecting valid responses with `Output validation error: expected string, received undefined`. Caught by nightly e2e (ENG-87 fixup of ENG-84).
- Fix(fred): `build_manifest_preview` now throws `INVALID_CONFIG` when called with `services: {}`. Previously the empty stack round-tripped into a single-service classification (since `isStackManifest` returns false for empty services), producing misleading `services: unknown field` and `image: required` validation errors. The function's docstring promises that hard structural failures throw — empty services qualifies (ENG-84).
- Fix(fred): replace the literal NUL byte (`U+0000`) embedded in `manifest.ts:387` with the explicit `'\0'` escape. Code behavior is unchanged (it was, and still is, checking for NUL — matching the env-name "cannot contain '=' or NUL" error message); the source is now reviewable in editors and `git diff` without the NUL being silently rendered as a space (ENG-84).
- Fix(fred): clarify `check_deployment_readiness.missing_steps` strings to spell out that `fund_credit` lives on the `manifest-mcp-lease` server, not fred. The `manifest-agent` plugin connects to all four servers so the tool is reachable, but the previous wording could mislead any host that wires fewer (ENG-84).
- Fix(fred): cap `available_sku_names` in `check_deployment_readiness` to 50 entries so a large catalog cannot bloat MCP responses. The chain query is bounded by `MAX_PAGE_LIMIT` (1000); 50 mirrors the spirit of the existing 10-item slice in the `missing_steps` "Pick one of: …" message. The exact `size` lookup still uses the full unbounded `Map` (ENG-84).
- Fix(fred): cross-service `depends_on` validation in `validateManifest` now uses a precomputed Set of service names instead of `Array.includes` inside a nested loop. Linear in total dep edges instead of O(services × deps × services). Practical impact at typical 1–10 services is negligible; the change is for clarity (ENG-84).
- Fix(fred): reject ports > 65535 in `validateManifest`. The previous `PORT_KEY_RE` permitted up to 5 digits (allowing 65536–99999), so a manifest with `"70000/tcp"` could silently pass `build_manifest_preview` even though the error message claimed 1–65535. Now post-checks the captured port via the existing `validatePort()` helper, mirroring the `expose` block (ENG-84).
- Fix(core): `structuredResponse` now applies the optional `replacer` to `structuredContent` (not just the text fallback). Round-trips through `JSON.parse(JSON.stringify(data, replacer))` so the over-the-wire payload is JSON-safe even when callers pass values like `BigInt` that the SDK can't serialize directly. Closes the abstraction footgun where the parameter implied BigInt support but the wire path silently bypassed the replacer (ENG-84).
- Feat(chain/lease/fred): retrofit `outputSchema` on the high-value tools that previously returned text-only JSON. `cosmos_estimate_fee`, `credit_balance`, `browse_catalog`, `app_status`, `app_diagnostics`, `app_releases`, `update_app`, and `deploy_app` now declare their structured output and emit `structuredContent` alongside the JSON text fallback. Clients that validate against `outputSchema` get type-checked responses; clients that don't keep working unchanged (ENG-84).
- Feat(fred): register three MCP prompts via `registerPrompt`: `deploy-containerized-app` (full deploy lifecycle with explicit confirmation gate, parameterized by image/port/size), `diagnose-failing-app` (triage flow combining app_status + app_diagnostics + get_logs for a given lease_uuid), and `shutdown-all-leases` (close-all workflow that lists active leases first and confirms before broadcasting). Adds the `prompts: {}` capability. Prompts give MCP hosts ready-made workflows the LLM can invoke without rebuilding the orchestration each time (ENG-84).
- Feat(fred): expose three MCP resources via `registerResource`: `manifest://leases/active` (caller's active+pending leases), `manifest://leases/recent` (last 50 leases of any state, reverse order), and `manifest://providers` (provider catalog snapshot, chain-side only). Adds the `resources: {}` capability to the fred server. Resources let an agent pull live context up-front instead of repeatedly polling tools (ENG-84).
- Feat(fred): add `check_deployment_readiness` MCP tool — a single-call pre-flight that returns wallet balances, credit account status, SKU availability, and a human-readable `missing_steps` list before `deploy_app`. Lets agents decide whether to fund credits, switch SKU, or top up the wallet without making three separate queries. Provider `allowed_registries` is operator config and not exposed via chain or public API, so `ready: true` does not guarantee `image`'s registry is allowed; the upload step is the runtime gate (ENG-84).
- Feat(fred): `deploy_app` and `wait_for_app_ready` now emit `notifications/progress` when the client passes a `progressToken` (or sets `onprogress` via the SDK). Progress messages cover the lease-created milestone and each provider poll iteration with the current `LeaseState` and `provision_status`. Both tools also forward the request's `AbortSignal` so a cancelled MCP request stops the upload/poll cleanly. No-op when the client doesn't request progress (ENG-84).
- Feat(fred): add `build_manifest_preview` MCP tool that builds, validates, and SHA-256-hashes a deployment manifest without touching the chain or any provider. Accepts a raw JSON `manifest` string OR structured fields mirroring `deploy_app` (image+port, or services). Returns the canonical `manifest_json`, the `meta_hash_hex` that would be recorded on-chain, and an inline `validation` result enumerating any rule violations (env-name blocklist, `fred.*` label prefix, port format, tmpfs limits, RFC 1123 service names, depends_on placement, unknown fields). Use this before `deploy_app` to reject obviously-broken manifests without paying for a lease (ENG-84).
- Feat(fred): export `metaHashHex`, `validateManifest`, and `ManifestValidationResult`/`ManifestFormat` from the package. The same `metaHashHex` helper now backs `deploy_app`'s on-chain meta-hash so a preview's hash is structurally guaranteed to match the eventual lease's `meta_hash` (ENG-84).
- Feat(fred): add `wait_for_app_ready` MCP tool that wraps `pollLeaseUntilReady` so agents can wait on a lease reaching `LEASE_STATE_ACTIVE` without re-implementing the polling loop. Accepts `timeout_seconds` (1–600) and `interval_seconds` (1–60); declares an `outputSchema` with `lease_uuid`, `provider_uuid`, `provider_url`, `state`, and the raw provider `status` payload (ENG-84).
- Feat(core): add `structuredResponse` helper alongside `jsonResponse` for tools that declare an `outputSchema`. Returns both `structuredContent` (the typed payload) and a JSON `text` fallback so older clients keep working (ENG-84).
- Feat(core): add Proof-of-Authority (`poa`), tokenfactory, and IBC transfer (`ibc-transfer`) modules with query and transaction routing through `cosmos_query`/`cosmos_tx`/`cosmos_estimate_fee`. Tokenfactory `update-params` is intentionally not exposed pending an upstream `manifestjs` codegen fix (`MsgUpdateParams.params` is wired to `cosmos.bank.v1beta1.Params` instead of the local tokenfactory `Params`).
- Fix(core): validate `poa create-validator` JSON input with a strict zod schema; reject unknown keys, validate validator address valoper prefix, and base64-decode the `pubkey.value` so `Any.encode` produces correct wire bytes.
- Fix(core): require non-empty `source-port` and `source-channel` on `ibc-transfer transfer` instead of forwarding blank strings to the chain.
